# Relational database design

Status: PROPOSED, ADR-003. PostgreSQL logical specification, not executable migrations. Domain authority: [questions](../specifications/QUESTION_SCHEMA.md), [assembly](../specifications/EXAM_ASSEMBLY_SPEC.md), [attempts](../specifications/EXAM_ENGINE_SPEC.md). Factory tables are implemented by early Track A (AI-001/FACTORY-001), independently of website completion; no speculative psychometric tables are required in MVP.

## Conventions

Unless stated otherwise, tables have UUID `id` PK, `created_at timestamptz`, `created_by` FK to local users (nullable for system events with explicit service actor). Mutable projections additionally have `updated_at`, monotonically increasing `revision`, and append-only audit events. Immutable versions never have mutable content fields. UTC throughout; integer counts/revisions/durations; exact numeric for percentages and money. JSONB stores validated discriminated content, not foreign-key arrays as a substitute for relational integrity.

Every FK has an index unless its leading columns are already indexed. Every composite FK below requires a matching UNIQUE target tuple, including (source_version_id,id) on rights_decisions, (question_version_id,id) on reviews, (attempt_id,id) on score_runs and (id,taxonomy_version_id) on question_versions. Referenced historical content uses ON DELETE RESTRICT. All UUID/key/foreign constraints are database-enforced; cross-row business invariants use reviewed transactions and, for immutability, triggers and role restrictions. Schema validators run before insert; JSON object/type/required-key checks and bounded sizes run at DB boundary too. Do not pretend application-only checks protect direct database writes.

Approval and eligible pointer update occur atomically under the publication lock; selecting a newer version does not rewrite the previous version or review. Referenced rights decisions remain historical evidence even after revocation.

| form_slots | form_id FK, slot_id UUID, section_id, ordinal, question_id, question_version_id, bundle_id nullable, public_snapshot JSONB, snapshot_hash | PK(form_id,slot_id); UNIQUE(form_id,ordinal), UNIQUE(form_id,question_id); composite FKs to section and question version; immutable |
| form_slot_secrets | form_id, slot_id, key_snapshot JSONB, explanation_snapshot JSONB, policy_version, secret_hash | PK/FK(form_id,slot_id) → form_slots; private immutable storage |
| form_assets | form_id FK, asset_version_id FK, purpose | PK(form_id,asset_version_id,purpose); snapshots retain exact bytes by immutable object key |
| question_exposure | question_id PK/FK, sealed_form_count bigint, projection_watermark | Optional analytics projection of distinct sealed forms; nonnegative; never stock/eligibility cap; rebuildable including withdrawals |

Form sealing is one transaction: selected-version/rights checks, snapshot construction, snapshot hash and all slots. For personal creation that transaction also includes owned attempt, first-history writes, allocation revision and idempotency receipt. Analytics updates are rebuildable and not required to acknowledge creation. Partial forms are never visible. Retain source IDs and version references alongside copied snapshots for incident propagation and audit. Use restrictive database grants plus immutability triggers on versions, form sections/slots/secrets; privilege escalation or migration-user access is not an ordinary app workflow.

## Attempts, grading and reliability

|---|---|---|
| attempts | user_id FK, form_id FK, form_mode, reuse_mode, reuse_policy_version, state, started_at, deadline_at, closed_at, terminal_reason, cancellation_reason nullable, grading_status, latest_score_id nullable, invalidation_reason | UNIQUE(id,form_id); UNIQUE(form_id) WHERE form_mode=PERSONALIZED_PRACTICE; proposed H1 UNIQUE(user_id,form_id) WHERE state IN ('CREATED','IN_PROGRESS'); index(user_id,created_at DESC); partial index(deadline_at) WHERE state=IN_PROGRESS; partial index(form_id,created_at) WHERE state=CREATED; clock fields required for started states |
| attempt_sections | attempt_id, form_id, section_id, starts_at, ends_at | PK(attempt_id,section_id); composite FKs to attempt/form and form_sections; CHECK(end>start); fixed once start commits |
| answers | attempt_id, form_id, slot_id, value JSONB, revision, saved_at | PK(attempt_id,slot_id); composite FK(attempt_id,form_id) → attempts and (form_id,slot_id) → form_slots; revision>0; prevents answering another form's slot |
| score_runs | attempt_id FK, policy_version, input_hash, correct_count, total_count, percentage numeric(5,2), section_totals JSONB, supersedes_id nullable FK, reason | UNIQUE(attempt_id,policy_version,input_hash); 0≤correct≤total and total>0; immutable |
| score_items | score_run_id FK, form_id, slot_id, earned smallint | PK(score_run_id,slot_id); FK to form_slots; earned IN(0,1); scoring transaction ensures run belongs to same attempt form |
| result_releases | attempt_id FK, score_run_id FK, policy_version, released_at, revoked_at nullable, reason | UNIQUE(attempt_id,score_run_id); composite FK prevents releasing another attempt's score; revocation audited |
| idempotency_records | actor_id FK, route_scope, key, request_hash, response_status, safe_response JSONB, resource_id, related_attempt_id nullable FK, completed_at, expires_at nullable | UNIQUE(actor_id,route_scope,key); scope includes target ID; attempt-linked rows pinned while unresolved; insert/result committed with business transaction |
| rate_limit_buckets | scope enum USER_CREATE, USER_SAVE or ATTEMPT_SAVE, subject_id, tokens numeric, refilled_at timestamptz | PK(scope,subject_id); no answer content; pseudonymous subject identifier; transactional shared counters; see API limits |
| jobs | kind, dedup_key, payload_ref, state, available_at, attempts, max_attempts, lease_owner/token, lease_until, last_error_code | UNIQUE(kind,dedup_key); partial index(state,available_at); no secret keys in payload |
| audit_events | actor_id nullable FK, service_actor nullable, action, entity_type/id, before_revision, after_revision, reason, request_id | Append-only; index(entity_type,entity_id,created_at); exactly one actor identity; restrict content/PII |

All save/submit/expire/grade commands serialize writes on the attempt row. Where a command also needs bank-publication consistency, acquire the shared bank lock before attempt/availability locks as specified in assembly; never acquire allocation lock after an attempt lock. Closure and grade-job insert commit together. Answer updates use expectedRevision and require IN_PROGRESS plus active time window after lock acquisition. Trigger rejects modifications to answers of closed attempts; any privileged repair requires a documented incident, never ordinary write access. Score insertion, score items, attempt GRADED transition and release are atomic; exact score inputs are hashed in slot order. Submitted answers themselves are frozen and retained, making input hash verifiable.

Job claiming uses transactional row locks with SKIP LOCKED, a bounded lease and fencing token. An expired lease can be reclaimed; stale workers cannot finalize after losing ownership. Side effects must still be idempotent because delivery is at least once. Retry backoff and FAILED_FINAL require operator action after configured attempts. Grade jobs use `attemptId:policyVersion:inputHash` dedup key. There is no Redis requirement.

## Retention, deletion and migrations

Proposed defaults pending ADR-006: keep account-linked attempt history 12 months after closure, operational logs 30 days, generation raw responses 30 days, idempotency records at least 7 days and through the attempt lifecycle, backups 30 days; audit/rights evidence retention needs legal-owner decision. These are not legal requirements or approved deletion schedules. Automatic deletion remains disabled until approval; production launch cannot proceed with undefined retention.

After approval, account deletion removes identity-provider linkage/PII and either deletes dependent personal records through a controlled purge or retains genuinely anonymized records only with a documented lawful purpose. Pseudonymization alone is not anonymization. Database subject tombstones preserve necessary FK/audit structure without retaining login identifiers. Legal hold/erasure decisions specify affected backups and assets; enforce deletion again after restore. Content immutability prevents ordinary edits, not lawful erasure: exceptional removal requires an audited purge manifest and affected-form invalidation.

Question/source versions referenced by forms are not hard-deleted through normal APIs; use quarantine/retire/withdrawal. Unreferenced rejected drafts can be purged under approved policy. Object removal requires a reference check across question/stimulus/form/explanation assets. Never cascade-delete historical exams when retiring a question.

Migration verification must test a fresh database and upgrading a populated previous schema, constraint failures, immutable-record updates and transaction races. Review SQL even when generated by an ORM. Index JSON properties only after observed queries; relational section/workflow/user/deadline indexes cover initial access patterns. Lock ordering and isolation are explicit implementation contracts, tested on real PostgreSQL rather than SQLite.

## Reconciliation constraints (PROPOSED, ADR-003/004/006)

H1–H3 in ADR-004 still require owner selection. The proposed active-attempt partial unique index does not replace UNIQUE(id,form_id), which remains a composite FK target. On different-key races map only that named unique violation to CONCURRENT_ATTEMPT_EXISTS after checking ownership; do not expose arbitrary constraint errors. Lazy cancellation/expiry clears stale active rows before deciding conflict; unrelated active rows are never forcibly cancelled. Personal forms remain limited to one attempt even after closure; fixed forms may be retaken explicitly after closure. Existing grading dedup keys remain unchanged.

CANCELLED requires started_at/deadline_at null, closed_at non-null, cancellation_reason in FORM_WITHDRAWN/RIGHTS_BLOCKED/ADMISSION_CLOSED; terminal_reason remains null. The periodic existing worker and request-path guards use the same idempotent command. Admission/withdrawal lock ordering is specified in the engine; immutable start times are separate from editable admission metadata. Current window changes never shorten a running attempt's timer.

At sealing assert total section duration <=21600 seconds, total slot count <=200, and each section's duration/count/type exactly matches its immutable blueprint, all in the sealing transaction. Compare actual slot counts, not only stored question_count fields. Ordinary row CHECK constraints remain local; this design does not rely on cross-row CHECK support. A mismatch rolls back form, slots and any personal attempt/history/receipt together; usage projections derive only committed forms. Tests must bypass the outer blueprint validator to exercise this defense.

Exposure projection repair counts distinct ALL sealed forms per question, including withdrawn ones; it is audited and uses a consistent snapshot/watermark with idempotent catch-up, not global eligibility reservations. No active-only recount or arbitrary reset. Answers remain one latest row per `(attempt_id,slot_id)`; revision does not denote stored history. No new answer-history table is authorized.

Attempt-linked idempotency records (create/start/save/submit) have related_attempt_id and expires_at=NULL while state is CREATED/IN_PROGRESS/SUBMITTED/EXPIRED, including failed-final grading pending recovery. After GRADED/CANCELLED/INVALIDATED, cleanup may set expiry no earlier than max(completed_at, finalization time)+7 days. Finalization time is the audited state-transition time (GRADED uses the atomic successful score/release timestamp), not the earlier submission closed_at. Cleanup locks the related attempt first and rechecks state; NULL is pinned, never expired. The minimum seven-day floor also applies to non-attempt records from completed_at. Owner-approved erasure/retention still governs eventual removal; this is a correctness lower bound, not permission for indefinite personal-data storage. After eligible deletion a retry may create a new attempt only if current admission/active-attempt and stable-history allocation guards allow it. Do not tie replay solely to the original form window, which may be extended.

Save bucket rows use server-derived local user ID/owned attempt ID and capacity/refill from API contract; enforce nonnegative tokens. Claim/update both buckets in deterministic scope+subject order in a short separate transaction, commit before taking the attempt lock. Concurrent replicas share state. Initialize a missing bucket full; idle rows may be deleted only after enough time to refill completely and with no in-flight update (row lock), so cleanup cannot manufacture extra capacity. User/attempt subject references are validated by the rate-limit module; these ephemeral polymorphic keys are not domain-history FKs. Failed authorization creates no arbitrary-ID bucket. No Redis/service is introduced; load validation must include the added DB work.

## Phase 02.75 schema delta: reuse and factory (PROPOSED ADR-007/008)

Existing question identities/versions/secrets, sources/rights, taxonomy, stimuli/bundles, duplicate groups, validation_runs, reviews, audit_events, jobs and all form/score tables are reused. No second approved bank, answer-history store, generation queue or duplicate personalized slot schema is added.

Inventory analysis is the immutable snapshot embedded in factory_batches, not another live inventory database. Batch status/report counts derive from work items, receipts, validation/review and eligible-pointer state; counters are cached projections only. Configs may be version-controlled files, but persisted resolved copies ensure a scheduled run is reproducible without a particular checkout.

Personal attempt integrity: attempts.form_mode matches forms.mode by composite FK (id,mode unique on forms); a personal attempt's (form_id,form_mode,user_id) matches (id,mode,owner_user_id). Apply that owner FK only to personal mode using a nullable personal_owner_reference/composite constraint or an equivalent insert trigger; fixed forms have null owner and permit many users. Enforce the mode/reuse combination table in reuse policy. UNIQUE(form_id) for personal attempts prevents cloning/reuse. Enforce history.first_attempt_id belongs to the same user on insert; allow SET NULL on approved old-attempt purge while retaining compact identity history. These references do not grant read access; API always checks ownership.

NEW_ONLY writes take student_allocation_state FOR UPDATE, then shared publication lock and current membership/history checks. Each strict history insert must be new; unique conflict aborts/replans. Review/fixed insert first-history only for absent identities. History plus revision, personal sealed form/attempt and idempotency receipt commit atomically. An equivalence merge takes exclusive publication lock, updates canonical membership/alias and bank revision, never mutates old manifests or forms. Current-history exclusion joins stable historical question IDs to current groups; this eliminates a redundant user-group ledger and stale-group repair jobs.

Factory atomic boundaries: create batch/plan and scheduled dedup key once; reserve call budget before network; provider call outside transactions; persist run response before import; import one question/bundle and its sources/provenance/receipts together; mark item completion in that same import transaction. Duplicate worker deliveries hit existing jobs/fencing and import receipts. Large batches commit incrementally. Existing jobs own leases, no generation_jobs table. Validation and human review append existing records; publication alone changes approved eligibility and bank revision. Factory service role has no write permission for approval/eligible pointers or read permission for user/attempt/history tables.

Privacy delta: compact student_question_history and allocation state must outlive ordinary 12-month result retention for an active account (proposed account-lifetime retention); otherwise NEW_ONLY would silently repeat older identities. It stores no answers, is still personal data, and requires owner retention review. Erasure removes history and account linking through a controlled user-locked purge; no guarantee across erased/new accounts. Personal manifests include exclusion sets and must follow the same protection/erasure rules. Factory retention of runs/packages/receipts must preserve minimum provenance for any published version; expiring raw LLM output must not delete rights/answer-review evidence needed for continued publication.

Analytics: distinct sealed_form_count comes from form_slots; student assignment/start/completion counts derive from attempts+form_slots, with fixed-form use counted per attempt. Do not equate these metrics. No decrement/removal of shared questions when any user receives them. Factory inventory views count currently eligible distinct identities/groups/bundles, not remaining global exposure tokens.
