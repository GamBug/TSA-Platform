# Relational database design

Status: PROPOSED, ADR-003, except the owner-approved ADR-004 H1 global active-attempt constraint, H2 admission semantics and H3 one-domain MVP tests. PostgreSQL logical specification, not executable migrations. Domain authority: [questions](../specifications/QUESTION_SCHEMA.md), [assembly](../specifications/EXAM_ASSEMBLY_SPEC.md), [attempts](../specifications/EXAM_ENGINE_SPEC.md). Factory tables are implemented by early Track A (AI-001/FACTORY-001), independently of website completion; no speculative psychometric tables are required in MVP.

## Conventions

Unless stated otherwise, tables have UUID `id` PK, `created_at timestamptz`, `created_by` FK to local users (nullable for system events with explicit service actor). Mutable projections additionally have `updated_at`, monotonically increasing `revision`, and append-only audit events. Immutable versions never have mutable content fields. UTC throughout; integer counts/revisions/durations; exact numeric for percentages and money. JSONB stores validated discriminated content, not foreign-key arrays as a substitute for relational integrity.

Every FK has an index unless its leading columns are already indexed. Every composite FK below requires a matching UNIQUE target tuple, including (source_version_id,id) on rights_decisions, (question_version_id,id) on reviews, (id,user_id) and (id,form_id) on attempts, (attempt_id,id) and (id,form_id) on score_runs, and (id,taxonomy_version_id) on question_versions. Referenced historical content uses ON DELETE RESTRICT. All UUID/key/foreign constraints are database-enforced; cross-row business invariants use reviewed transactions and, for immutability, triggers and role restrictions. Schema validators run before insert; JSON object/type/required-key checks and bounded sizes run at DB boundary too. Do not pretend application-only checks protect direct database writes.

Form sealing is one transaction: selected-version/rights checks, snapshot construction, snapshot hash and all slots. For personal creation that transaction also includes owned attempt, first-history writes, allocation revision and idempotency receipt. Analytics updates are rebuildable and not required to acknowledge creation. Partial forms are never visible. Retain source IDs and version references alongside copied snapshots for incident propagation and audit. Use restrictive database grants plus immutability triggers on versions, form sections/slots/secrets; privilege escalation or migration-user access is not an ordinary app workflow.

| jobs | kind, dedup_key, payload_ref, state, available_at, attempts, max_attempts, lease_owner/token, lease_until, last_error_code | UNIQUE(kind,dedup_key); partial index(state,available_at); no secret keys in payload |
| audit_events | actor_id nullable FK, service_actor nullable, action, entity_type/id, before_revision, after_revision, reason, request_id | Append-only; index(entity_type,entity_id,created_at); exactly one actor identity; restrict content/PII |

All save/submit/expire/grade commands serialize writes on the attempt row. Where a command also needs bank-publication consistency, acquire the shared bank lock before attempt/availability locks as specified in assembly; never acquire allocation lock after an attempt lock. Closure and grade-job insert commit together. Answer updates use expectedRevision and require IN_PROGRESS plus active time window after lock acquisition. Trigger rejects modifications to answers of closed attempts; any privileged repair requires a documented incident, never ordinary write access. Score insertion, score items, attempt GRADED transition and release are atomic; exact score inputs are hashed in slot order. Submitted answers themselves are frozen and retained, making input hash verifiable.

Job claiming uses transactional row locks with SKIP LOCKED, a bounded lease and fencing token. An expired lease can be reclaimed; stale workers cannot finalize after losing ownership. Side effects must still be idempotent because delivery is at least once. Retry backoff and FAILED_FINAL require operator action after configured attempts. Grade jobs use `attemptId:policyVersion:inputHash` dedup key. There is no Redis requirement.

## Retention, deletion and migrations

Proposed defaults pending ADR-006: keep account-linked attempt history 12 months after closure, operational logs 30 days, generation raw responses 30 days, idempotency records at least 7 days and through the attempt lifecycle, backups 30 days; audit/rights evidence retention needs legal-owner decision. These are not legal requirements or approved deletion schedules. Automatic deletion remains disabled until approval; production launch cannot proceed with undefined retention.

After approval, account deletion removes identity-provider linkage/PII and either deletes dependent personal records through a controlled purge or retains genuinely anonymized records only with a documented lawful purpose. Pseudonymization alone is not anonymization. Database subject tombstones preserve necessary FK/audit structure without retaining login identifiers. Legal hold/erasure decisions specify affected backups and assets; enforce deletion again after restore. Content immutability prevents ordinary edits, not lawful erasure: exceptional removal requires an audited purge manifest and affected-form invalidation.

Question/source versions referenced by forms are not hard-deleted through normal APIs; use quarantine/retire/withdrawal. Unreferenced rejected drafts can be purged under approved policy. Object removal requires a reference check across question/stimulus/form/explanation assets. Never cascade-delete historical exams when retiring a question.

Migration verification must test a fresh database and upgrading a populated previous schema, constraint failures, immutable-record updates and transaction races. Review SQL even when generated by an ORM. Index JSON properties only after observed queries; relational section/workflow/user/deadline indexes cover initial access patterns. Lock ordering and isolation are explicit implementation contracts, tested on real PostgreSQL rather than SQLite.

## Reconciliation constraints (ADR-004 scoped approvals; remainder PROPOSED)

H1 is approved globally; H2 admission, H3 one-domain MVP tests, the Start TTL, and non-retroactive ordinary admission-schedule edits are also scoped owner approvals. ADR-004 as a whole remains PROPOSED. The proposed database design enforces H1 exactly:

```sql
CREATE UNIQUE INDEX uq_one_active_attempt_per_user
ON attempts (user_id)
WHERE state IN ('CREATED', 'IN_PROGRESS');
```

The partial unique index does not replace UNIQUE(id,form_id), which remains a composite FK target, or the personal form's lifetime single-attempt constraint. On different-key races, map only violation of `uq_one_active_attempt_per_user` to CONCURRENT_ATTEMPT_EXISTS after checking caller ownership; do not expose arbitrary constraint errors. Under the same per-user allocation lock, reconcile an elapsed IN_PROGRESS attempt through the existing expiry/grade-job command and cancel a CREATED attempt whose persisted `start_before_at` has elapsed, before checking for an active attempt or allocating a new form. Use the existing audited, idempotent system cancellation command; use START_TTL_EXPIRED only for an elapsed approved TTL bound. For an existing CREATED attempt, ordinary admission schedule edits are not an unusable-attempt guard and must not produce ADMISSION_CLOSED; only explicit withdrawal, rights blocking, or security invalidation remains an overriding restriction. Never cancel a valid active attempt just to admit another. Personal forms remain limited to one attempt even after closure; fixed forms may be retaken explicitly after closure. Existing grading dedup keys remain unchanged.

`attempts.start_before_at TIMESTAMPTZ NOT NULL` is calculated using authoritative database/server time during each successful creation and committed atomically with the attempt, assignment history and creation receipt. A restricted write path and immutability trigger reject later updates to this field, including state changes; retain it after closure for history and audit. `created_at < start_before_at` is required. A matching idempotency replay reads the original receipt backed by the same stored deadline; it never recomputes one from current `form_availability` or `blueprint_offerings`. The API projects `CreationReceipt.startBefore` and, only while CREATED, `AttemptView.startBefore` from this field. Do not denormalize a domain on attempts: for MVP the immutable form has exactly one `form_sections` row whose domain supplies attempt, result and history labels. `attempt_sections` and score-run section totals reference that same form snapshot; each attempt's `deadline_at` and score remain independent. Generic multiple `form_sections` rows remain representable until a future runtime profile is separately approved.

The approved H2 interval `[available_from, available_until)` gates creation, not completion. The separately owner-approved MVP start TTL is an additional mandatory 600-second reservation bound: `start_before_at = min(created_at + 600 seconds, admission_until_at_creation)`. Missing or invalid required TTL configuration rejects offering activation/attempt creation and never falls back to unlimited start time. An existing CREATED attempt starts only when server time is strictly before its persisted bound, it remains CREATED, the authenticated student owns it, and form status plus withdrawal, rights, and security guards permit access. It must not be rechecked against mutable current admission bounds. On start set that attempt's own `started_at` and `deadline_at = started_at + its immutable one-section duration`; admission closure alone never shortens it. Ordinary availability edits affect future creation only: they cannot mutate, recalculate, cancel, or invalidate an existing CREATED attempt's `start_before_at` or committed start eligibility. Explicit withdrawal, rights revocation and security invalidation remain separate overriding guards. Neither ordinary edit nor those guards rewrites the immutable form or the stored bound.

CANCELLED requires started_at/deadline_at null, closed_at non-null, cancellation_reason in FORM_WITHDRAWN/RIGHTS_BLOCKED/ADMISSION_CLOSED/START_TTL_EXPIRED; terminal_reason remains null. The periodic existing worker and request-path guards use the same idempotent command. Admission/withdrawal lock ordering is specified in the engine; immutable start times are separate from editable admission metadata. Current window changes never shorten a running attempt's timer.

At sealing assert total section duration <=21600 seconds, total slot count <=200, and each section's duration/count/type exactly matches its immutable blueprint, all in the sealing transaction. Compare actual slot counts, not only stored question_count fields. Ordinary row CHECK constraints remain local; this design does not rely on cross-row CHECK support. A mismatch rolls back form, slots and any personal attempt/history/receipt together; usage projections derive only committed forms. Tests must bypass the outer blueprint validator to exercise this defense.

Exposure projection repair counts distinct ALL sealed forms per question, including withdrawn ones; it is audited and uses a consistent snapshot/watermark with idempotent catch-up, not global eligibility reservations. No active-only recount or arbitrary reset. Answers remain one latest row per `(attempt_id,slot_id)`; revision does not denote stored history. No new answer-history table is authorized.

Attempt-linked idempotency records (create/start/save/submit) have related_attempt_id and expires_at=NULL while state is CREATED/IN_PROGRESS/SUBMITTED/EXPIRED, including failed-final grading pending recovery. After GRADED/CANCELLED/INVALIDATED, cleanup may set expiry no earlier than max(completed_at, finalization time)+7 days. Finalization time is the audited state-transition time (GRADED uses the atomic successful score/release timestamp), not the earlier submission closed_at. Cleanup locks the related attempt first and rechecks state; NULL is pinned, never expired. The minimum seven-day floor also applies to non-attempt records from completed_at. Owner-approved erasure/retention still governs eventual removal; this is a correctness lower bound, not permission for indefinite personal-data storage. After eligible deletion a retry may create a new attempt only if current admission/active-attempt and stable-history allocation guards allow it. Do not tie replay solely to the original form window, which may be extended.

Save bucket rows use server-derived local user ID/owned attempt ID and capacity/refill from API contract; enforce nonnegative tokens. Claim/update both buckets in deterministic scope+subject order in a short separate transaction, commit before taking the attempt lock. Concurrent replicas share state. Initialize a missing bucket full; idle rows may be deleted only after enough time to refill completely and with no in-flight update (row lock), so cleanup cannot manufacture extra capacity. User/attempt subject references are validated by the rate-limit module; these ephemeral polymorphic keys are not domain-history FKs. Failed authorization creates no arbitrary-ID bucket. No Redis/service is introduced; load validation must include the added DB work.

## Phase 02.75 schema delta: reuse and factory (PROPOSED ADR-007/008)

This is a proposed PostgreSQL migration contract, not approval or executable DDL. Factory produces restricted drafts, Bank alone reviews and publishes the current eligible version, Website allocates immutable exam snapshots, and the exam worker scores them. They share the existing bank, `jobs`, `assembly_runs`, forms, attempts and scores. A separately deployed Factory may import through the same Bank command and durable receipt. No Factory-to-Website database access or student-path model call is needed.

### Necessary tables and ownership

All new FK targets below are `ON DELETE RESTRICT` in ordinary operation except the specifically nullable `first_attempt_id`. Each UUID reference has a B-tree index unless it leads a PK/UNIQUE/index already shown. State fields use constrained enums/checks; all counts, revisions and monetary minor units are nonnegative. The named owner is the only component allowed to perform the stated write command; migration credentials are separate.

### Transaction boundaries and concurrency

1. **Factory plan and dispatch.** Create each batch, frozen plan, items and deduplicated jobs in a short transaction. Reserve worst-case cost by inserting a `generation_runs` row and updating the batch reservation under a row lock before each provider call. Network calls hold no database transaction. Persist response/checkpoint once with the current job fencing token; reconcile uncertain charges before releasing reserved budget. Import one candidate or entire bundle with versions, secrets, provenance, assets, receipts and item checkpoint in one transaction. Retry reads the receipt/hash and never overwrites an existing immutable version. Large batches commit per unit.
2. **Bank publication.** Reviewers append `validation_runs` and `reviews` against the immutable version hash; a later edit creates a new version. An authorized Bank command takes the exclusive bank-publication transaction advisory lock, rechecks rights interval/source decision, exact hash, validators, independent human review, duplicate resolution and singleton/canonical group membership, then changes `question_workflow` and `questions.eligible_version_id` and increments `bank_state.eligibility_revision` once in that transaction. Revoke/quarantine/merge/offering changes use the same guard and revision. Rollback leaves the old eligible pointer and revision intact. Publication never rewrites prior versions or sealed forms.
3. **Website allocation.** Capture history and eligible manifest in a short consistent read; search without locks. On commit, create-if-absent and lock `student_allocation_state` FOR UPDATE, recheck the idempotency key/request hash, then take the shared bank-publication lock. Return a matching committed creation receipt before active-state conflict handling, including when its attempt has since closed. Reconcile the user's stale active attempt under its row lock and commit its expiry/cancellation and required grading job before admitting a replacement; if one valid active attempt remains, return its owner-safe ID as CONCURRENT_ATTEMPT_EXISTS without allocating anything. Re-read revision, offering, rights, eligible versions, current canonical groups and that user's first-history rows. A changed input aborts this allocation transaction and creates a new manifest/`assembly_runs` attempt under the same request key; bounded replans precede `CONCURRENT_MODIFICATION`. Revalidate within-form group/enemy exclusions, bundles, taxonomy/quota/section aggregates and the complete sealed snapshot. For NEW_ONLY, every selected stable ID and current canonical group must be absent from history; strict history inserts must be new, and uniqueness conflict aborts rather than `ON CONFLICT DO NOTHING`. Seal form/sections/slots/private keys/assets, owned CREATED attempt with immutable `start_before_at`, all first-history rows, allocation revision and success idempotency receipt in the same transaction. REVIEW_ALLOWED and FIXED_AS_PUBLISHED may repeat only by explicit mode; they add missing first-history rows under the same lock. Fixed publication alone does not assign a student. Any failed allocation rolls back all new form/history/revision/receipt rows; no partial form or global stock reservation survives. A stale-attempt finalization committed before a later allocation failure remains final.
4. **Attempt and grading.** Existing start/save/submit/expire commands lock the attempt row; close and grade-job insertion commit together. Grading reads frozen answers and form secret snapshots, writes exactly one immutable run/items/aggregate and release with attempt state in one transaction, and uses the existing dedup key. Failed aggregate/slot assertion rolls back the whole grade. Regrading creates a new run with `supersedes_id`, never edits prior scores.

Lock order for every creation mode is user row → shared publication guard → existing attempt row if reconciling stale active state → availability row. Bank publication holds the exclusive guard for short bank writes and does not acquire user/attempt locks; later cancellation fanout uses separate transactions. Start/access requiring bank consistency take shared guard before attempt/availability. Save/submit/grade do not acquire the user row after an attempt lock. Distinct-key same-user creation requests serialize on the user row across modes; the second rechecks state and either finds the first active attempt or may allocate after its closure. The named unique index is the final database guard if a write path misses that serialization; on its violation, roll back the attempted creation and fetch only the authenticated user's active ID. Distinct students can allocate the same identity concurrently. A later group merge changes future exclusions, not historical committed forms. Real two-connection PostgreSQL barrier tests are required before this is a verified concurrency guarantee.

`student_question_history` is the minimal durable first-assignment ledger: `attempts` joined to immutable `form_slots` can derive complete per-attempt assignments only while every attempt/form is retained. It cannot preserve NEW_ONLY after shorter attempt/result retention or provide a small indexed first-assignment lookup. No second per-attempt slot history, user-group ledger, rendered/view history, answer-edit history or per-student bank copy is proposed. Current canonical membership is joined at allocation time, so a later merge excludes all newly equivalent identities without rewriting history. `question_exposure` remains an optional rebuildable count of distinct sealed forms, including withdrawn forms, never an eligibility cap.

### Authorization, retention and migration implications

Factory DB credentials claim only factory job kinds, read approved sources and aggregate inventory, and write plan/run/draft/validation through scoped commands. They cannot read `users`, `student_allocation_state`, `student_question_history`, attempts, answers, private form snapshots or manifests, and cannot approve/publish. Bank reviewer/publisher identity is a separate human-authorized role; author/operator and independent approver cannot be the same person. Website uses server-derived user IDs, checks form/attempt ownership before any read/write, and cannot grant itself Bank or Factory authority. Exam worker reads only owned grading jobs and private snapshots needed to score. Restrictive grants, views/commands, row ownership checks and negative authorization tests are all required; FKs alone do not authorize access.

Proposed active-account history retention must outlive the shorter proposed 12-month result retention, or strict NEW_ONLY would forget prior assignments. History, allocation revision and personal manifests are protected personal data; approved erasure requires a controlled user-locked purge and cannot promise no-repeat after account removal/new account creation. Published versions retain minimum source/rights, validation, review and import evidence even if raw model responses expire under an approved policy. Normal deletion of referenced versions, forms, score runs and receipts is restricted; exceptional erasure/incident removal uses audited invalidation/purge rather than an ordinary mutable edit.

Migration implementation should expand/backfill/contract: add nullable provenance links and new tables/constraints, backfill first assignments from retained attempts plus `form_slots` (including fixed/review attempts and never-started attempts), create singleton memberships and canonicalize confirmed merges, then turn on strict allocation only after a complete historical coverage audit. If old assignments are unavailable, record the coverage gap and obtain an explicit owner migration policy; never label an incomplete backfill strict NEW_ONLY. Add indexes concurrently where PostgreSQL requires it, validate FKs/checks on populated data, and test a fresh install and populated upgrade with duplicate, mismatched owner/version/form, rollback, two-connection allocation and publication races. A compatibility rollback disables new allocation/publication paths while preserving immutable versions, history, receipts and exams; it does not delete or rewrite them. Coordinate actual migration file ownership between DATA-001 and FACTORY-001. All constraints and transaction behavior here remain REQUIRES_VERIFICATION until implemented and tested on PostgreSQL.


## G1 shared job dispatch contract — job-dispatch/1

The final G1 audit freezes a minimal internal transport for existing logical work,
not a new queue or database migration. Exact strict fields: schemaVersion
`job-dispatch/1`, jobId (lowercase UUID), kind, dedupKey, payloadRef, state.
`factory_produce_unit` names the existing factory_items production-unit job;
`exam_grade_attempt` names the existing attempt-closure grading job. These are
technical names for already specified responsibilities, not new workflow stages.
No wildcard kind is accepted. Additional kinds require coordinated versioning.

FACTORY executor contracts accept only factory_produce_unit; EXAM accepts only
exam_grade_attempt. Executor identity must be server-derived by later adapters;
contract validation is not authentication or DB permission enforcement. Shared
states retain exactly QUEUED, RUNNING, SUCCEEDED, FAILED_RETRYABLE, FAILED_FINAL,
CANCELLED. dedupKey and payloadRef are opaque nonblank strings preserved verbatim;
actual domain-derived deduplication, payload lookup and secret-handling remain
producer/adapter responsibilities. Embed no payload, credentials or publication
assertion in this dispatch shape. Emit it only through the internal package entry.

This envelope is not the complete jobs persistence row. Leases, fencing tokens,
attempt counters, timing, retries, transactions and grants remain DATA-001,
AUTH-001, EXAM-002 and FACTORY task work. This technical encoding changes no
approved product behavior, existing root schema, public route or dependency.
