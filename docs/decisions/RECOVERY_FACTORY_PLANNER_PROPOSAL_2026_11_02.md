# RECOVERY-009 — Factory planner and atomic reservation proposal

- Status: **PROPOSED**. No owner architecture approval or implementation authorization for these config, planner, persistence, or live-dispatch choices is recorded here.
- Date: 2026-11-02.
- Scope: engineering design for the bounded FACTORY-002 planner and FACTORY-003 execution/reservation prerequisites. This is not executable DDL, a new shared contract, or a production plan.
- Review: independent read-only review is requested; no review outcome is implied until recorded.

## Existing contract and database boundary

The planner is defined by the current [Question Factory specification](../specifications/QUESTION_FACTORY_SPEC.md#versioned-configuration-and-inventory-planning), [AI pipeline contract](../specifications/AI_QUESTION_PIPELINE.md#provider-neutral-contract), and [database design](../architecture/DATABASE_DESIGN.md#necessary-tables-and-ownership). The deterministic [fake adapter](../guides/FAKE_GENERATION_ADAPTER.md) is now available as an in-memory prerequisite. It does not add durable configuration, inventory, plan, reservation, or recovery behavior.

The existing provider-neutral `generation/1`, `ProviderResult`, and `ProviderError` contracts remain unchanged. Candidates remain unknown and untrusted until the existing validation and Bank workflow accepts the exact immutable version. The plan and internal tables below are proposed persistence shapes only; they do not extend `question/1`, `factory-package/2`, `job-dispatch/1`, or any student contract.

The checked-in migrations already define both `factory_produce_unit` and `exam_grade_attempt` in `tsa.jobs`; `job-dispatch/1` and `JobExecutor` already accept only the corresponding FACTORY and EXAM pair ([jobs DDL](../../db/migrations/002_exam_integrity.sql#L308), [G1 dispatch contract](../../docs/architecture/DATABASE_DESIGN.md#g1-shared-job-dispatch-contract--job-dispatch1), [contract parser](../../packages/contracts/src/jobs.ts#L1)). No new job kind or queue is proposed.

Current checked-in ACLs are asymmetric by design: `tsa_factory` is created NOLOGIN, can read only factory-kind jobs, and has a column-limited job update grant protected by factory-kind RLS; `tsa_exam` has separate exam-kind policies. `tsa_factory` also has narrow source, current-rights and taxonomy reads, not student or private form data ([base grants](../../db/migrations/001_bank_core.sql#L9), [job policies/grants](../../db/migrations/002_exam_integrity.sql#L1260), [source grants](../../db/migrations/001_bank_core.sql#L498)). The implemented `exam_worker_claim` only selects `exam_grade_attempt`; the SECURITY DEFINER claim/load/finish/fail functions are executable by the separate NOLOGIN `tsa_exam_worker` role ([claim](../../db/migrations/014_exam_grading.sql#L78), [function grants](../../db/migrations/014_exam_grading.sql#L231)). There is no implemented Factory claim/reserve/finalize function or durable `factory_batches`, `factory_items`, or `generation_runs` table in migrations.

`tsa_factory` has no `INSERT` grant on `tsa.jobs`. Therefore the proposal assigns plan creation to one checked `tsa.factory_plan_commit` SECURITY DEFINER command, not direct application SQL or a broader table grant. It validates caller capability, schedule/manual uniqueness, hashes, candidate and capacity caps, current source rights, and immutable config/snapshot before inserting the batch, items, and existing factory-kind jobs in one transaction. The function returns only job-dispatch references; no source text, candidate content, or credential is placed in `payload_ref`.

This ACL summary is verified against checked-in migration SQL, not a live target `pg_catalog` snapshot; no rollout database was identified for inspection. Disposable-cluster migration tests can assert the catalog grants and RLS directly. A later target rollout must compare its actual ACLs with the approved migration before deployment.

## Proposed strict immutable inputs

All proposal schemas reject unknown keys, duplicate IDs, noncanonical integers, non-finite numbers, invalid enum values, and unknown schema versions. Config, inventory, and plan JSON each have a 2 MiB, depth-32, 50,000-node hard ceiling; aggregate batch candidate count is at most 500. Each persisted config, snapshot, and plan stores its schema version, canonicalization version, and SHA-256 hash. Canonicalization is UTF-8 canonical JSON with recursively sorted object keys, preserved array order, no implicit normalization, and explicit `factory-canonical-json/1` identity. IDs and hashes are private Factory records, never student DTO fields.

| Record | Proposed required fields and bounds |
|---|---|
| `factory-config/1` | Immutable `configName` (1–128 chars), `versionNo` (positive int), `taxonomyVersionId`, `producerNamespace` (1–128 chars), ordered immutable quota and unit-template arrays (each at most 256), source-version IDs (1–50, unique), prompt and validator versions (1–128 chars), output schema exactly `question/1`, selected `adapterRevision` and `modelRevision`, and a SHA-256 hash of the resolved value. No mutable alias may be used as a batch input. |
| `factory-inventory/1` | Strict `snapshotId` UUID, `capturedAt` UTC, taxonomy ID, `bankEligibilityRevision` canonical nonnegative BIGINT string, rights manifest/hash, aggregate eligible/pending counts by at most 256 quota cells (each 0–2,000,000), at most 50 source-version/hash/current-decision/revision/validity records, at most 256 complete-bundle counts, and explicit remaining validator/reviewer/token/spend capacity. No question body, answer key, user/history row, or raw source text is copied into the snapshot. |
| Quota cell | `section` in MATH/READING/SCIENCE; `skillId` (1–128 chars); `interactionType` in the three `generation/1` values; nullable M1/M2/M3 cognitive level; nullable EASY/MEDIUM/HARD target difficulty; `targetEligibleDistinct` integer 0–2,000,000; `weightPermille` integer 0–1,000,000. The full tuple is unique. Target difficulty remains an authoring target, not an official score or difficulty claim. |
| Unit template | Stable `templateId`; kind QUESTION or BUNDLE; ordered `members` with one to twenty members. QUESTION has exactly one member. Each member pins section, one to 32 taxonomy skill IDs, interaction type, nullable cognitive level and target difficulty. BUNDLE also pins its complete stimulus/source specification and all member ordinals. Each member becomes one candidate and one `generation/1` request with `count: 1`; bundles may use several calls but are one indivisible planning, checkpoint, validation, and import unit. |
| Adapter capability snapshot | Immutable provider-returned `adapterRevision`, `modelRevision`, supported sections/types/output schemas, per-call candidate/token/byte limits, and a canonical capability hash. Every planned call must fit these limits. The current fake allows 256 candidates per result but only 128 registered fixture cases; therefore one-case-per-member fixture runs cover at most 128 calls/candidates. A 500-candidate durable batch requires an authorized adapter with sufficient per-call and aggregate capability; it is never implied by the fake. |
| Budget and capacity | One explicit ISO currency and `minorUnitDigits` (0–6); maximum spend in canonical decimal integer minor units, bounded to signed PostgreSQL BIGINT; maximum batch input/output tokens in bounded decimal integer strings; per-call input ≤100,000 and output ≤50,000 tokens; per-call `maxCostMicros` is a nonnegative safe integer compatible with the existing request contract. Pin integer pricing revision/rates per token-million and no implicit FX. `maxExternalCallsPerCandidate` is 1–2 (GENERATE and at most one separately approved VERIFY), `maxAttempts` is 1–3, concurrency is 1–2, candidate cap is 1–500, and validator/reviewer capacity is each 0–500 candidates. |
| Pending-yield policy | `pendingYieldPermille` integer 0–1,000 and `yieldEvidenceVersion`. Use fixed-point floor rounding. If no measured, owner-accepted evidence exists, the value is zero; unknown acceptance never becomes approved stock. |
| Schedule version | Separate immutable schedule revision pins IANA timezone and period rule. Timezone/revision edits affect future periods only; each batch stores the resolved UTC period. The schedule does not alter or embed provider credentials. |

Token counts, retry multiplication, rates, and spend sums use checked `BigInt` arithmetic in application code and bounded integer columns in PostgreSQL. Convert to JavaScript numbers only after proving `Number.isSafeInteger`. In this proposal, `costMicros` means millionths of the one currency pinned for that adapter/config; no FX or currency field is added to G1. With integer rates in microcurrency per million tokens, calculate `ceil((inputTokens × inputRate + outputTokens × outputRate) / 1,000,000)` microcurrency, then convert to minor units by ceiling division by `10^(6 - minorUnitDigits)`. Reject overflow, missing pricing, precision above six digits, or an adapter unable to report that pinned currency before live dispatch. A reported `costMicros: null` is unknown cost, never zero.

The adapter capability hash is included in the resolved config, plan hash, and each call's run record. If capabilities later shrink, resume pauses or fails that call; it does not silently widen a request or re-plan. `GenerationRequest` remains unchanged, including its `count`, source-version IDs, schema version, and budget fields.

Planner target difficulty, bundle membership, schedule period, currency, and pricing do not exist in `GenerationRequest`. They stay in the strict config/plan and private invocation/run manifest. The selected version-pinned adapter/prompt mapping may apply supported target context through its existing approved-source/prompt inputs; if it cannot honor that context through the unchanged G1 signature, the planner rejects that template before dispatch. It must not overload `skillIds`, `requestId`, or other request fields. Only the existing `budget.maxCostMicros` crosses the request boundary; its currency/rate interpretation is pinned outside the request.

## Proposed inventory and deterministic plan

`factory-inventory/1` is one bounded immutable snapshot: `capturedAt` UTC; taxonomy ID; Bank `eligibility_revision`; aggregate approved eligible counts by quota cell and complete-bundle template; current source version/content hashes plus current rights decision IDs/revisions/validity horizons; aggregate pending counts by generation, validation, and review stage; currently committed/uncertain call reservations; and validator/reviewer capacity. Pending stages are mutually exclusive: each candidate member is counted once at its latest durable stage using its item/member/candidate ordinal, never once as generated and again as validating or awaiting review. Counts contain no candidate body or identifier. The snapshot contains no per-student history, user IDs, attempts, answers, or arbitrary private identifiers. A restricted Bank-owned aggregate command/view is required because `tsa_factory` has no broad question-bank query grant.

At plan freeze, separately filter every configured generation source against its current immutable content hash, `source_rights` decision/revision, active attestor, validity interval, territory, and `GENERATE` permission. `DISPLAY`-only, expired, revoked, UNKNOWN, or disabled-attestor sources are ineligible for generation. This authorization is distinct from approved-stock counts for student selection, which use the existing Bank eligibility command. Pin only eligible generation sources into unit specs; do not include blocked sources in a plan and hope the dispatch check catches them later.

Approved supply counts distinct eligible stable question identities, with the current confirmed equivalence group counted once; eligible bundles count complete feasible bundles. Counts may overlap across skill cells. Pending drafts, validation work, and review-queue items are recorded separately and never satisfy actual stock eligibility or assembly.

For each quota cell, compute `pendingExpected = floor(pendingCandidates × pendingYieldPermille / 1000)` using integer arithmetic and `deficit = max(0, targetEligibleDistinct - approvedDistinct - pendingExpected)`. This projected number is only a planning estimate; persisted approved counts never include pending work. Rank positive deficits by descending `deficit × weightPermille`, then a fixed enum order (section, interaction type, cognitive level, difficulty) and UTF-8 lexical skill/template IDs. The order and algorithm version are part of the hash.

On every iteration, scan positive-deficit cells in ranked order and, within each cell, compatible templates in stable `templateId` order. Choose the first whole unit that fits all remaining caps and strictly advances at least one remaining requested-coverage deficit. If every template for one cell is infeasible, advance to the next ranked cell; an unfillable high-ranked cell cannot starve a feasible lower-ranked cell. After selecting a unit, update requested coverage/capacity and restart the ranked scan. Declare no fit only after one full scan over all remaining positive cells and compatible templates selects nothing. Simulate all candidate members before adding a QUESTION or BUNDLE: each candidate increases the global candidate count by exactly one and credits each still-deficient compatible skill cell by at most one. Multi-skill overlap can reduce multiple cell deficits, but it never adds multiple candidates to the global budget. Apply a bundle's complete member set as one simulation. Never split a bundle to fit a quota or import half of it. An indivisible bundle may oversupply a target if at least one member advances a remaining deficit and every member fits the hard caps; record all excess rather than discarding members. Skip a template if its full candidate count, per-call limits, worst-case retries, token cost, validator capacity, or human-review slots exceed any hard cap. Assigned draft coverage is not predicted or actual human acceptance; report the predicted-acceptance estimate separately (unknown unless supported) and never write these assignments into eligible-stock counts.

Continue until every projected deficit is zero or no complete compatible unit fits. A zero-unit plan is an explicit completed empty plan with a reason; a partial plan records its `CAPACITY`, `BUDGET`, `NO_COMPATIBLE_UNIT`, or rights stop reason. The hard batch cap counts candidate questions across all members and bundles and never exceeds 500. Review and validator caps also count every candidate member, not merely bundle/job count. A request for 500 candidates is a maximum draft plan, not a promise of 500 outputs, accepted questions, or publications.

`factory-plan/1` pins: producer namespace and batch key; schedule identity/UTC period or manual operator idempotency key; config version/hash; inventory snapshot ID/hash/revision; adapter capability hash; planner and canonicalization versions; ordered units with stable `itemKey`, ordinal, QUESTION/BUNDLE kind, spec hash, all member request specs/source IDs, planned candidate count, calls/retry bound and per-gate capacity estimates; aggregate candidate/token/spend upper bounds; and a strict stop/empty reason. It has at most 500 units/candidates; members are one to twenty per unit; calls are bounded by configured generation/verifier calls and at most three attempts each. `planHash = SHA-256(canonical JSON without the planHash field)`. An `itemKey` derives only from producer namespace, logical batch key, ordinal, and canonical unit-spec hash. Stable call identity adds member/call ordinal, kind, and attempt number; a response hash cannot replace item or import-receipt identity.

## Identity, replay and manual/scheduled conflict rules

- A scheduled period's identity is `(scheduleId, resolved scheduledForUtc)`. The partial unique constraint on that tuple remains independent of schedule revision. On retry, resolve that tuple first and return its stored immutable plan before reading current config or inventory. Editing a schedule revision changes only future periods and can never create a second batch for the same UTC period.
- A manual run uses a caller-supplied, operator-authorized idempotency key and the existing unique `(producerNamespace, batchKey)`. Same key plus same resolved config/snapshot intent returns the existing plan. Same key with changed config, snapshot, adapter capabilities, or planner version returns `IDEMPOTENCY_CONFLICT`; it never overwrites the frozen row.
- An operator-triggered run scoped to a schedule/period is the same scheduled logical batch, not an ad hoc manual batch. It stores both `schedule_id` and `scheduled_for_utc`, resolves the same unique tuple before config/inventory work, and separately audits the human initiator/request key. Matching intent replays; changed intent conflicts. Thus the existing proposed partial unique active-schedule index and schedule-row lock apply across every period and both cron/operator initiation: operator period A and cron period B cannot both be active for one schedule. Only ad hoc manual batches have both schedule columns null. A deliberately fresh ad hoc inventory plan requires an explicit new manual key and `supersedesBatchId` after the prior batch is safely stopped; no scheduled-period identity is reused. Old batches/runs/receipts and uncertain costs remain immutable, and all batches still consume any shared budget-period cap.
- `resume --batch-id` loads the frozen config, snapshot, plan, item keys, and checkpoints. It never resolves a new alias, recalculates deficits, or silently changes source/rights/capability hashes. If rights or adapter constraints have changed, the affected call is blocked and the batch is paused or failed safely. A deliberately fresh plan is a new, explicitly linked batch.

Manual and scheduled invocation share one short transaction to claim the logical batch identity, persist the frozen batch/inventory/plan, create one `factory_items` row and one deduplicated existing `factory_produce_unit` job per unit, and record their hashes. Because `tsa_factory` cannot insert jobs directly, only `factory_plan_commit` performs these writes after validating server-derived operator/role context and strict schema/hash/cap inputs. Lock schedule/identity rows; check existing unique identities before snapshot work; enforce one active batch per schedule; and rely on unique constraints as the final race guard. Same-key races return the committed matching plan or a typed conflict. There is no job-per-candidate for bundles and no second queue.

## Rights, reservations, fencing and recovery

The source list is first filtered at plan freeze and refreshed against immutable source-version content hashes and the *current* `source_rights` decision immediately before each external call. `DISPLAY` is insufficient: generation requires a current, active decision permitting `GENERATE`, valid for the execution territory and time, with an active attestor, across every source/dependency in the unit. The existing `bank_source_display_allowed()` helper proves display only; it is not a generation-rights check. A narrowly scoped Bank-owned generation-rights query/function and revision-aware call guard are a migration prerequisite. Budget reservation alone is not dispatch permission. A separate checked `factory_begin_dispatch` transaction rechecks rights, all source hashes and the current lease, then records the run's immutable dispatch-authorization timestamp and a deadline no later than one second after authorization, the lease deadline, or the earliest rights expiry. Its commit is the proposed authorization linearization point. The worker must invoke the provider immediately before that deadline; delayed handoff cannot use stale permission. A revocation committed before this guard wins and blocks the call; later revocation stops calls not yet authorized but cannot undo already authorized/in-flight data transfer. Any dispatch marker means a crash may have sent data, even if the worker actually crashed before network I/O, so recovery treats it conservatively as UNCERTAIN. The owner must approve this bounded handoff/linearization rule; no claim of an atomic database-plus-provider transaction is made.

Plan estimates are not spend reservations. They bound worst-case candidate, verifier, retry, token, and review demand but are not added to actual batch spend. A proposed `factory_budget_periods` row (scope, currency, period, cap, settled and held projections) serializes any approved operator/provider period cap shared by batches; if no such cap is approved, only the immutable batch cap applies. Its counters are audited projections of `generation_runs`, never a second cost ledger.

Any Factory transaction that reads current Bank rights follows one lock order: shared Bank advisory/Bank-state guard first, then schedule/logical identity where applicable, budget-period rows in stable key order, batch, job, item, and run. Bank publication must never acquire Factory budget/job locks. Ledger-only reconciliation may omit Bank guards but cannot acquire them later in that transaction. This avoids budget→Bank versus Bank→budget cycles; no examination/user/attempt lock participates. For each GENERATE or VERIFY attempt, reservation then recomputes `settled spend + all RESERVED/UNCERTAIN spend + this call upper bound` with checked integers, enforces token/call/candidate caps, and inserts exactly one `generation_runs` reservation under unique `(jobId, callKind, callOrdinal, attemptNo)`. It updates projections and reservation in one commit. An existing exact run replays without reserving twice. Reservation and subsequent begin-dispatch authorization both commit before the provider invocation; no DB transaction or Bank lock remains open during provider I/O.

Proposed reservation transitions are monotonic:

| Event | `generation_runs.reservation_state` | Budget effect |
|---|---|---|
| Call upper bound reserved before dispatch | RESERVED | Hold the full upper bound. |
| Provider envelope with valid usage metadata and known `costMicros` (candidate content may still fail validation) | SETTLED | Persist exact actual cost and response/run hashes, even if actual cost exceeds the reservation or cap; mark a budget overrun and stop new dispatch. Never roll back or erase an incurred charge to preserve a cap. |
| Successful response with `costMicros: null` or otherwise unknown charge | UNCERTAIN | Persist response/checkpoint but keep the full hold until reconciled; no further dispatch can spend the held amount. |
| Provider proves a pre-dispatch rejection or confirms no charge | RELEASED | Release once under the current fencing token; append the proof/reference. |
| Timeout, disconnect, worker death, or lost response after dispatch may have begun | UNCERTAIN | Keep the full hold. Lease expiry alone never releases it. Reconcile provider evidence; settle actual/conservative cost or release only with proof of no charge. |

Worker settlements require a live matching fence. Recovery after job cancellation, terminal state, or lease expiry instead uses a narrow `factory_reconcile_run` command granted only to a separate NOLOGIN `tsa_factory_reconciler` capability with server-derived authorized operator identity. It accepts bounded external evidence/proof plus the expected run revision, locks the same budget/run rows, and compare-and-sets one UNCERTAIN/unused reservation to SETTLED or RELEASED exactly once. It preserves original fence/dispatch evidence, audits the reconciler and proof hash, and cannot claim a job, authorize a provider call, publish, or delete a charge. Thus terminal jobs cannot strand holds merely because no worker lease can be acquired. Any marked dispatch needs reconciliation proof; an unmarked reservation may be released only after the checked command has fenced out every possible begin-dispatch for that run. Known actual totals use checked SQL NUMERIC/application BigInt projections even when an overrun exceeds a signed-BIGINT budget cap; caps restrict admissions, never the ability to preserve actual charge evidence.

The executor claims only `factory_produce_unit` with `FOR UPDATE SKIP LOCKED`; lease duration is 1–300 seconds and every claim increments the existing `lease_token`. Each checkpoint/finalization transaction verifies factory role membership, job kind/state, lease owner, token and live deadline. It writes response/checkpoint, run settlement, item state, and job terminal/retry state atomically. A stale worker returns `LOST_LEASE` and cannot overwrite data. An external call can execute twice after a crash; exactly-once provider execution/billing is not promised. `ProviderError.retryable` alone is never proof that dispatch did not occur or cost nothing. Only a durable pre-dispatch/no-charge outcome permits bounded backoff for RATE_LIMIT/TIMEOUT/UNAVAILABLE; if dispatch may have begun, mark UNCERTAIN and stop automatic retry pending reconciliation, unless an explicitly approved provider contract proves same-key replay is idempotent. REFUSAL, INVALID_OUTPUT, rights failure, and budget exhaustion do not auto-retry. In-flight uncertainty consumes/reserves budget before any new attempt. If known actual spend exceeds the held upper bound or any budget cap, commit the actual amount and overage evidence, mark the batch `PAUSED/BUDGET`, and block subsequent dispatch; the cap controls admissions and cannot promise a provider will never overcharge.

Each candidate remains restricted run evidence until strict validation passes. Complete bundle validation/import and its receipt/checkpoint are atomic per unit through the existing Bank import and review workflow. A matching receipt/hash replays existing IDs; changed content under the same producer/batch/item/ordinal fails conflict. No Factory command can create an APPROVED transition or eligible pointer. Cancellation stops unstarted work, keeps completed drafts and run evidence, and accounts for every in-flight reservation.

## Expansion, explicit privilege cutover, and roles

Proposed future migration (next available number after 026; no file is created here) adds immutable `factory_config_versions`, audited `factory_schedules`, `factory_batches` (frozen config, inventory, plan/hash, schedule tuple or ad hoc manual identity, currency, operator/initiator audit), optional approved-scope `factory_budget_periods` for cross-batch caps, `factory_items` (one QUESTION/BUNDLE unit, item key, job link, checkpoint), and `generation_runs` (per external call/attempt, pricing/input/source/response hashes, reservation and settlement state). Scheduled/operator-period batches share UNIQUE(schedule_id,scheduled_for_utc) and UNIQUE(schedule_id) while active; only ad hoc manual rows have null schedule columns. Constraints include the current `jobs` foreign key, stable uniqueness keys, finite state enums, positive planned candidate count, signed-BIGINT-safe budget fields, immutable input/hash columns, and append-only run outcomes. `factory_plan_commit` is the only plan/job insert path; no broad `INSERT` grant is added to `tsa_factory`. No `generation_jobs` table, second Bank, second review store, canonical question change, or blanket Factory question read is proposed.

Preserve every existing `tsa.jobs` row, exam kind, grading function, `tsa_exam_worker` grant, attempt, answer, score, result, and history row. Do not rewrite the `jobs.kind` check, `JobDispatch/1`, or `parseJobDispatchForExecutor`; do not widen EXECUTE grants on exam routines. Grant `factory_plan_commit` only to the existing NOLOGIN `tsa_factory` planner capability after it validates server-derived operator context. Add separate NOLOGIN `tsa_factory_worker` (Factory-only SECURITY DEFINER claim/reserve/begin-dispatch/checkpoint/finalize) and `tsa_factory_reconciler` (reconciliation only) capabilities with fixed search paths, explicit role membership and appropriate fence/revision checks; deployment login membership remains outside DDL. `tsa_factory` remains NOLOGIN and cannot claim grading jobs or read users, student allocation/history, attempts, answers, or private snapshots. After compatibility proof, replace its direct lease/state `UPDATE` grant with these checked commands; preserve its source/taxonomy reads and factory-row RLS. Only a restricted Bank-owned aggregate command may supply eligible-stock counts, and only a Bank import command may create draft receipts.

The table/function expansion is additive, but removing the preexisting direct Factory UPDATE grant is an explicit privilege-contract change, not an expand-only claim. Stage it as a separately approved, audited cutover before enabling the new dispatcher; until then its activation remains off. The new worker/reconciler login capabilities must not inherit `tsa_factory` or other direct table-update bypasses. Inventory and retire any old Factory caller relying on the grant, retain legacy behavior in expansion-stage tests, and change only the expected Factory UPDATE grant at cutover; exam worker and source/taxonomy grants stay stable. This proposal does not authorize that cutover merely by existing.

Migration preflight compares existing role attributes/ACLs and every existing job/function before and after against a precise allowed-difference list. Prove old exam claim/finish and grading history unchanged, and that Factory cannot access exam jobs/student/private tables. Test fresh and populated026 expansion, replay, and an injected late-DDL failure that rolls back all new objects/grants without changing existing rows/security. Cutover tests separately prove the planned UPDATE removal and checked-command path. Down/disable retains batches/runs/drafts and exam jobs; operational rollback disables dispatch and never resets tokens, refunds uncertain calls, deletes receipts, or removes Bank drafts.
